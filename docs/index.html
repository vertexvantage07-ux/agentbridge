agentbridge

The layer between an AI agent and the tools it calls, for when those tools are unreliable.

Go MIT licensed Zero dependencies Standard library only v1.0.0

Every number on this page was produced by running the library. Attempt counts, call counts and elapsed times are measured at runtime by the same code path a caller would use — not written by hand, not estimated. The run below is recorded verbatim.

What it did, and what a naive caller does instead

ScenarioWhat agentbridge didCallsElapsedNaive caller
transient failure
tool fails twice, then succeeds (a network blip)		 retried, succeeded on attempt 3 (3 call records) 371ms aborts on the first error; the whole run fails on a blip
permanent failure
tool rejects the input; retrying can never help		 gave up after 1 call in 0ms — no retries wasted 10ms retries 4 times, pays 4× for the same rejection, reports it late
circuit breaker
dependency dead and staying dead; 6 calls attempted		 circuit opened; 3 of 6 calls never touched the tool (outcome=circuit_open) 30ms calls a dead API 6 times, gets rate-limited, and possibly billed
deadline
tool takes 3s; the call budget is 150ms		 gave up at the deadline instead of blocking 1170ms blocks the agent for 3s per attempt; a 10-step task loses 30s
telemetry
one call that fails, observed		 2 CallRecords emitted (tool, outcome, attempts, elapsed) 20ms no record; you find out from the customer, days later
health endpoint
what the library reports about itself		 {"tools":{"search_tool":{"circuit_open":false}},"broken":0} 10ms you cannot answer "is the agent healthy?" without inventing it

Read the first two rows together. A blip is worth retrying. A rejected input is not. Telling those two apart is the entire job, and a naive retry loop cannot do it — which is why the library classifies failures rather than counting them.

Reproduce this yourself

This page is a recorded run so it stays up permanently. The measuring code ships with the library, so you do not have to trust the recording:

go get github.com/vertexvantage07-ux/agentbridge@v1.0.0

go test ./...
# ok  github.com/vertexvantage07-ux/agentbridge/agentbridge

The full demo, which runs the real library against deliberately broken dependencies and streams the results, is in the repository under cmd/demo:

git clone https://github.com/vertexvantage07-ux/agentbridge
cd agentbridge && go run ./cmd/demo

Why the distinctions matter

BehaviourWhy
Retries transient failures with exponential backoff and full jitterSynchronised retries are how a service that just recovered gets knocked over again
Gives up immediately on permanent failuresA 400 retried four times is a bug, not resilience
Honours a server's own Retry-AfterBetter than a guessed delay, always
Per-attempt deadlinesA slow first attempt otherwise eats the retry budget, so retries become a single attempt
Per-tool circuit breakersOne dead dependency should not disable the whole agent
Structured telemetry per callDuration, attempts, outcome and failure kind — queryable, not guessed
Health viewLets the agent say "that tool is down" instead of appearing to hang

Using it

bridge := agentbridge.NewBridge[MyPayload](agentbridge.DefaultConfig(), nil)

result, err := bridge.Do(ctx, agentbridge.Tool[MyPayload]{
    Name: "charge_card",
    Call: func(ctx context.Context, in MyPayload) (MyPayload, error) {
        return gateway.Charge(ctx, in)
    },
}, payload)

One call site changes and the retries, the deadline, the breaker and the telemetry record for that tool exist. Adding the sixth tool is the same edit as the first.
